### The x86 UEFI image must be pflash

- `qemu-system-x86_64 -bios /opt/homebrew/share/qemu/edk2-x86_64-code.fd` exits 1 with `qemu: could not load PC BIOS '...edk2-x86_64-code.fd'` (measured here, twice: the log line on the seed transcript's command, and step 7).
- The same image given as `-M q35 -drive if=pflash,format=raw,readonly=on,file=...` reaches the UEFI shell (measured here). The aarch64 image does boot with `-bios` (measured here).

### Accelerators

- `qemu-system-aarch64 -accel help` lists `hvf` and `tcg`; `qemu-system-x86_64` and `qemu-system-riscv64` list `tcg` only (measured here). On this Mac, x86_64 and riscv64 guests are emulated, never accelerated.
- `-accel kvm` fails with `invalid accelerator kvm` (measured here).

### HVF nested virtualisation (EL2)

What Apple documents:

- Apple's Hypervisor framework has `hv_vm_config_get_el2_supported`, which "Returns a status value that indicates whether the current platform supports Exception Level 2 (EL2)", and `hv_vm_config_set_el2_enabled`, both introduced in macOS 15.0 ([Apple, hv_vm_config_get_el2_supported](https://developer.apple.com/documentation/hypervisor/hv_vm_config_get_el2_supported(_:)); [hv_vm_config_set_el2_enabled](https://developer.apple.com/documentation/hypervisor/hv_vm_config_set_el2_enabled(_:_:)); read through the pages' JSON).
- Neither page names the chips that support EL2 (same pages); a Linaro engineer made the same observation on qemu-devel and assumed M4 ([Alex Bennée, 2025-07-15](https://mail-archive.com/qemu-devel@nongnu.org/msg1127523.html)). The "M3 or later" requirement that third parties state is unverified: it appeared only in search-result summaries of a mailing-list reply and a UTM issue, not on a page of Apple's that was read.
- The framework does not give vCPUs a reset state; the entry level is set through `HV_REG_CPSR`'s M field ([Apple Developer Forums 775546](https://developer.apple.com/forums/thread/775546), the accepted answer by an Apple engineer).

What QEMU does:

- Mohamed Mediouni's series "HVF: Add support for platform vGIC and nested virtualisation" reached v21 on 2026-04-29 ([cover letter](https://patchew.org/QEMU/20260429190532.26538-1-mohamed@unpredictable.fr/)). Peter Maydell applied it to `target-arm.next` (same page, his reply).
- The commit "hw/arm, target/arm: nested virtualisation on HVF" ([d7a75ea](https://github.com/qemu/qemu/commit/d7a75ea483a57add78b559cd181293e0136cc8c8), 2026-05-05) is in v11.1.0 and not in v11.0.0 (measured here: `gh api repos/qemu/qemu/compare/d7a75ea...v11.1.0` gives `ahead`, against v11.0.0 `behind`). It queries `hv_vm_config_get_el2_supported` and fails with "Nested virtualization not supported on this system." when the answer is no (same commit, `target/arm/hvf/hvf.c`).
- The platform vGIC is the default for `virt-11.1` and later ([37863ff](https://github.com/qemu/qemu/commit/37863fff59e0), "hvf: arm: enable vGIC by default for virt-11.1 and later").

Limits reported in the v21 cover letter ([patchew](https://patchew.org/QEMU/20260429190532.26538-1-mohamed@unpredictable.fr/)):

- "the nested virtualisation implementation shipping as of macOS 26.3 is nVHE only (but it _does_ use VNCR as shipped)". Whether macOS 26.6 changed this is unverified.
- When the guest is at EL2 as the virtual timer fires, the interrupt is not delivered back (without the platform vGIC the exit does not fire; with it, the interrupt is lost). The reference ArmVirtQemu EDK2 build uses the virtual timer at EL2, "so it gets broken unless this patch is applied to edk2", which switches its generic-timer counter library from the virtual to the physical one.
- "when nested virt is enabled, no UI response within EDK2 and a permanent wait. Workaround: -boot menu=on,splash-time=0", filed with Apple as FB21649319.
- The series disables the Scalable Matrix Extension when nested virtualisation is active (patch 12 of 15, by its title; [patchew](https://patchew.org/QEMU/20260429190532.26538-1-mohamed@unpredictable.fr/)).

What was measured on this M4 Pro (QEMU 11.1.3, macOS 26.6.2):

- `-M virt,virtualization=on -accel hvf -cpu host` starts without an error (measured here). Given the check in d7a75ea above, this suggests the framework reports EL2 support on this chip; that is an inference, not a reading of the call's result.
- With it, EDK2 prints its banner and then nothing for 30 s, never reaching the boot manager; without `virtualization=on` the shell appears within 8 s (measured here). With `-boot menu=on,splash-time=0` added, the shell appears within 20 s (measured here), matching the cover letter's known issue.
- Under TCG, `-M virt,virtualization=on -cpu max` reaches the shell (measured here).
- Whether the firmware actually ran at EL2 was not checked; that is M1.1's spike.
- GitHub's macOS arm64 runners do not support nested virtualisation, "due to the limitation of Apple's Virtualization Framework" ([GitHub-hosted runners reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)), so this evidence cannot come from CI.

### The x86 VT-x gap

The maintainer has no x86 Linux hardware, so VT-x and KVM evidence must come from emulators or CI runners (log, 2026-11-27 decision). VT-x is the VMX extension, which software detects with `CPUID.01H:ECX.VMX[5] = 1` (`intel-sdm` 325462-093, §26.6 "Discovering Support for VMX", in `reference/text/intel-sdm.txt`). The options:

| Option | What is known | Not known |
|---|---|---|
| QEMU TCG | `-cpu max,+vmx` warns "TCG doesn't support requested feature: CPUID[eax=01h].ECX.vmx [bit 5]" and boots without it; `-cpu max,+svm` boots with no warning (measured here) | whether an SVM (AMD-V) hypervisor actually runs correctly under TCG: unverified, not tested |
| Bochs | 3.1 released 2026-08-23 ([release](https://github.com/bochs-emu/Bochs/releases/tag/REL_3_1_FINAL)); `configure` takes `--enable-vmx=[no|1|2]`, level 2 needs x86-64 and CPU level 6, and `--enable-svm` separately ([configure.ac at REL_3_1_FINAL](https://github.com/bochs-emu/Bochs/blob/REL_3_1_FINAL/bochs/configure.ac)); Homebrew's `bochs` 3.1 (LGPL-2.0-or-later) is built with `--enable-vmx=2` and `--enable-x86-64`, without `--enable-svm` ([formula at 117ce69](https://github.com/Homebrew/homebrew-core/blob/117ce6910070ac7d1b23941c7a6e439b7f22c1e0/Formula/b/bochs.rb)); changes since 3.1 list VMX and SVM bug fixes ([CHANGES](https://github.com/bochs-emu/Bochs/blob/master/bochs/CHANGES)) | which VMX features (EPT, VPID, unrestricted guest) level 2 covers: unverified; Bochs is not installed or run here |
| CI runners with KVM | GitHub-hosted Linux runners "support hardware acceleration for Android SDK tools" ([runners reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)); since 2024-04-02 this includes 2-vCPU runners, after a udev rule that opens the `kvm` device to the runner user ([changelog](https://github.blog/changelog/2024-04-02-github-actions-hardware-accelerated-android-virtualization-now-available/)) | whether the runners' CPUs are Intel (VT-x) or AMD (SVM), and whether KVM offers nested virtualisation to a guest there: unverified; a job reading `/dev/kvm`, the `vmx`/`svm` flags in `/proc/cpuinfo` and `/sys/module/kvm_intel/parameters/nested` would settle it |

For comparison, RISC-V's hypervisor extension is emulated: QEMU's default `virt` CPU reports `rv64imafdch` to OpenSBI (measured here), and `h` is the extension of `riscv-isa-manual` (release 20261127), Volume II, Chapter 5 "H Extension for Hypervisor Support" (`reference/text/riscv-isa-manual.txt`).

## 4. Verification tools and `build-std`

M1.3 decides the test strategy and verification tools, and M1.2 decides `build-std` ([spec §2](../chunks/m0.1-dev-environment/spec.md#2-goals-and-non-goals)); this section records their state on 2026-11-27. None of the tools below is installed here (measured here: `command -v cargo-kani cargo-verus`).

### Verus and the kernels verified with it

- **Verus** "is a tool for verifying the correctness of code written in Rust": specifications are checked statically by solvers, it supports "a subset of Rust", and it is "under *active development*" ([README](https://github.com/verus-lang/verus/blob/bfffda99218c0bf236937175f2acd69ba9219096/README.md)). Its papers are "Verus: Verifying Rust Programs using Linear Ghost Types" (OOPSLA 2023) and "Verus: A Practical Foundation for Systems Verification" (SOSP 2024) ([publications page](https://verus-lang.github.io/verus/publications-and-projects/)). MIT licence; the latest non-rolling release is `release/0.2026.11.22.1ce6a59`, and the repository pins Rust `1.100.0` with `rustc-dev`, the same stable version as this project (measured here: `gh api repos/verus-lang/verus`, its releases and `rust-toolchain.toml` at bfffda9).
- **Atmosphere** is "a full-featured microkernel with support for strict isolation in mixed-criticality systems", written in Rust with its functional correctness ("refinement of a high-level specification") proved in Verus: 6K lines of executable code, under 2.5 person-years, a proof-to-code ratio of 3.32:1, verification "in less than 20 seconds on a modern laptop" ([Chen et al., SOSP 2025, abstract](https://mars-research.github.io/doc/2025-sosp-atmo.pdf)). It runs on multiple CPUs "under a big lock" (same paper, §1). Its trusted computing base includes Verus, Z3, rustc, `core`, 172 lines of assembly and about 3,000 lines of trusted Rust for the IOMMU, APIC, IDT, TSS, GDT and `sysenter`, and its own boot loader (same paper, §5); those are x86 components, and the README boots it through GRUB's `multiboot2` from `x86_64-unknown-none` builds, so it is an x86-64 kernel. The repository is MIT, builds with Nix and an `atmo` tool extending Cargo, and pins Rust `1.99.1` (measured here: `gh api repos/mars-research/atmosphere`, README and `rust-toolchain.toml` at c7cece4).
- **Asterinas `vostd`** "provides a formally-verified version of OSTD", the library through which Asterinas confines `unsafe`; the current focus is OSTD's "*memory management* and *synchronization*", and the work is "ongoing" ([README at 1ee2aee](https://github.com/asterinas/vostd/blob/1ee2aeeeb5a72e47442e50dbefeaf33b1f46b9d9/README.md)). It uses its own fork of Verus, verifies for `x86_64-unknown-none` by default with RISC-V and LoongArch variants, and is tied to CortenMM (SOSP 2025) and three 2026 papers on proof generation with language models (same README). MPL-2.0; it pins Rust `1.100.0` (measured here: `gh api repos/asterinas/vostd`, `rust-toolchain.toml` at 1ee2aee).

### Miri, Kani and `loom`

| Tool | What it checks | Limits relevant to a kernel | Toolchain, state, licence |

### The state of `build-std`

- `-Zbuild-std` has existed, unstable, "since August 2019", and users who need it "are forced to use nightly" ([RFC 3873](https://rust-lang.github.io/rfcs/3873-build-std-context.html)). On stable 1.100.0, `cargo build -Zbuild-std=core` fails with "the `-Z` flag is only accepted on the nightly channel of Cargo" (measured here).
- The RFC series: 3873 (context, no change proposed), 3874 (`build-std.when = "always|never"`, and how Cargo builds the standard library on stable), 3875 (explicit dependencies such as `core = { builtin = true }`), and two not yet opened, `build-std="compatible"` and `build-std="match-profile"` ([RFC 3873](https://rust-lang.github.io/rfcs/3873-build-std-context.html); [RFC 3874](https://rust-lang.github.io/rfcs/3874-build-std-always.html); [RFC 3875](https://rust-lang.github.io/rfcs/3875-build-std-explicit-dependencies.html)). The three were merged on 2025-12-31, 2026-04-15 and 2026-05-04 (measured here: `gh api repos/rust-lang/rfcs/pulls/<n>`). Under RFC 3874 a target's `standard_library_support` field sets which crates can be built on stable; unset means nightly (RFC 3874). Using the standard library with custom target JSON is listed as not planned (RFC 3873).
- The 2026 project goal "build-std" (point of contact Adam Gemmell, accepted) is to "Complete the remaining design work for #3874 and #3875 and start on implementation"; it gives no stabilisation date ([goal page](https://goals.rust-lang.org/2026/build-std.html)). The page still calls 3874 and 3875 open for feedback, which predates their merge (measured here, above).
- This project's three targets are Tier 2 without host tools, `no_std` only ([platform support](https://doc.rust-lang.org/rustc/platform-support.html)), and rustup ships prebuilt `core`, `alloc` and `compiler_builtins` for each (measured here: `ls $(rustc --print sysroot)/lib/rustlib/<target>/lib`). So `build-std` is needed only for a custom target or a rebuilt `core`, which is M1.2's question.

## 5. CHERI

CHERI extends an instruction set with hardware capabilities; ISA version 9 is the Cambridge and SRI technical report UCAM-CL-TR-987, September 2023, 523 pages ([report page](https://www.cl.cam.ac.uk/techreports/UCAM-CL-TR-987.html)).

- **Arm:** Morello is "a prototype System-on-Chip (SoC) and development board, developed by Arm", a CHERI-extended Armv8.2-A Neoverse N1, AArch64 only, and "the ONLY physical implementation of this prototype architecture" ([Cambridge, Morello](https://www.cl.cam.ac.uk/research/security/ctsrd/cheri/cheri-morello.html)). Whether Arm plans CHERI for the A-profile is unverified: Cambridge's page says only that learnings "will be adopted into a mainstream extension to the Arm architecture" (same page), and Arm's own pages could not be read (§3).
- **RISC-V:** RISC-V International's `riscv-cheri` specification defines the RVY base (RV32Y, RV64Y), profiles and privileged extensions; the current snapshot, `v0.9.11-draft-12da558, 20261125`, says "DRAFT---NOT AN OFFICIAL RELEASE" and also "in the Stable state", and it is CC BY 4.0 and based on CHERI v9 ([specification](https://riscv.github.io/riscv-cheri/)). Tagged versions run from v0.9.9-ar20260707 to v0.9.10.1-ar20261013 ([versions](https://riscv.github.io/riscv-cheri/versions.html); measured here: `gh api repos/riscv/riscv-cheri/tags`); what "ar" stands for is not stated (same page). The task group's plan targeted a freeze on 2025-06-15 and Board ratification on 2025-09-29 ([CHERI Ratification Plan, updated 2025-04-18](https://riscv.atlassian.net/wiki/spaces/CTXX/pages/47022116/CHERI+Ratification+Plan)), but the ratified-specifications library lists no CHERI or RVY entry on 2026-11-27 ([library](https://docs.riscv.org/reference/home/index.html)). So it is not ratified; its exact stage (public review or later) is unverified, because the RISC-V status pages were truncated before any CHERI row.
- **Toolchains:** an LLVM RFC (2025-07-30) proposes upstreaming CHERI support for RISC-V, not Morello, and says RISC-V CHERI "is in the process of standardization as the Y extension" while existing implementations use the vendor extensions XCheri and XCheriot ([LLVM Discourse](https://discourse.llvm.org/t/rfc-upstream-target-support-for-cheri-enabled-architectures/87623)). rustc 1.100.0 has no CHERI target (measured here: `rustc --print target-list`).
- **QEMU:** upstream QEMU has no CHERI support: v11.1.0 has no CHERI file under `target/` (measured here: `gh api repos/qemu/qemu/contents/target/riscv?ref=v11.1.0`), and the installed 11.1.3 has no CHERI or Morello CPU model (measured here: `-cpu help`). CHERI-QEMU, which implements "the Arm Morello and CHERI-RISC-V instruction sets", has moved to the CHERI Alliance; `cheribuild`'s `cheri-std093-qemu` target builds the Alliance QEMU for "Draft RVY 0.9.3 and beyond", and the CTSRD-CHERI fork keeps "unstable CHERI research features" ([Cambridge, CHERI-QEMU](https://www.cl.cam.ac.uk/research/security/ctsrd/cheri/cheri-qemu.html)). The Alliance's `main` is based on QEMU 7.2.0 and its `alliance-8.0` branch on 8.0.0, with RISC-V decoders for RVY, the standard draft and v9; CTSRD's `qemu-cheri` is based on 7.0.0 (measured here: `gh api`, each branch's `VERSION`). Both READMEs say to build with `cheribuild` ([CHERI-Alliance/qemu](https://github.com/CHERI-Alliance/qemu); [CTSRD-CHERI/qemu](https://github.com/CTSRD-CHERI/qemu)); neither is in Homebrew (measured here: `brew search cheri` lists no CHERI package), and neither was built or run here, so whether they build on this Mac is unverified.

Three leads for M2, deciding nothing (the maintainer's choice, plan Deviations, step 8):

- **A raw kernel image from ELF.** The `llvm-tools` component is installed (log of step 1). Its `llvm-objcopy` is LLVM 23.1.5 and takes `-O`, "Alias for --output-target"; the sysroot also holds a `rust-objcopy` identical to it, plus `llvm-objdump`, `llvm-nm`, `llvm-size` and `rust-lld` (measured here: `--version`, `--help`, `cmp`, `ls` of the sysroot's `bin`). None is on `PATH` (measured here: `command -v rust-objcopy`). `cargo-binutils` provides `rust-<tool>` proxies and `cargo objcopy`-style subcommands that build first; it is "not an official Rust project", and the Rust project "makes no guarantee about the availability and the CLI of these tools" ([README at 57bef93](https://github.com/rust-embedded/cargo-binutils/blob/57bef9366464ad13dd383af02ef18de1ff126617/README.md)); v0.4.0, 2025-09-15 (measured here: `gh api`). Whether M2 needs a raw image at all depends on M1.2's boot path.
- **rust-analyzer and `no_std` crates.** `rust-analyzer.cargo.target` is one "Compilation target override" for the workspace ([configuration](https://rust-analyzer.github.io/book/configuration.html)); without it, rust-analyzer reads `build.target` from the Cargo configuration, else the host from `rustc -vV` ([target_tuple.rs at efc6ca7](https://github.com/rust-lang/rust-analyzer/blob/efc6ca74690b36e0b13961537ce043db912363f9/crates/project-model/src/toolchain_info/target_tuple.rs)). Separate `.cargo/config.toml` files per workspace member are not handled ([issue #16765](https://github.com/rust-lang/rust-analyzer/issues/16765), open). Cargo's per-crate `package.forced-target` is unstable ([unstable features, per-package-target](https://doc.rust-lang.org/cargo/reference/unstable.html); [tracking issue #9406](https://github.com/rust-lang/cargo/issues/9406), open). Whether rust-analyzer honours `forced-target` is unverified; a code search of its repository found no occurrence (measured here: `gh search code`). The installed rust-analyzer is 1.100.0 (measured here).
- **Homebrew version drift.** "Homebrew is a rolling release package manager", and `brew bundle` "does not and will not have" a lock file; `--no-upgrade` or `HOMEBREW_BUNDLE_NO_UPGRADE=1` stops upgrades but "does not pin versions" ([Brew Bundle and Brewfile](https://docs.brew.sh/Brew-Bundle-and-Brewfile)). `brew pin` prevents a package "from being upgraded" by `brew upgrade` ([manpage](https://docs.brew.sh/Manpage)). This project's only guard is `doctor`'s QEMU minimum of 11.1.0 ([spec §4.3](../chunks/m0.1-dev-environment/spec.md#43-cargo-xtask-doctor)).
