# Lessons: agent tooling (hooks, permissions, skills, container scripts)

- Status: Living (2026-11-28)

- **tooling-1.** A Claude Code hook blocks only by exiting 2, so its checker's own failure (a broken build, a missing tool) must map to 2 for risky input and to 0 for the rest: fail closed on the narrowest signal, not on anything the parser cannot read. Test it with real agent commands: multi-line scripts, heredocs and prose, `2>&1`, `| tail`, comments with apostrophes. *Why:* the push guard first blocked an ordinary commit (a heredoc mentioning `git push`), then let every push through while xtask failed to build (rust-engine-experiment M3.15). *From:* rust-engine-experiment M3.15 · *Confirmed:* 2026-11-15
- **tooling-2.** A hook that runs `cargo` builds in its own target directory nested under any existing one (`${CARGO_TARGET_DIR:-target}/<name>`) and sets an explicit `timeout`. *Why:* sharing the default target dir made the hook wait 37 s behind a concurrent build, and an absolute path inside the repository is shared by the host and the devcontainer (rust-engine-experiment M3.15). *From:* rust-engine-experiment M3.15 · *Confirmed:* 2026-11-15
- **tooling-3.** A `Bash(<tool> *)` allow rule accepts every flag of the tool; for cargo, `--config` (a `runner`) and `--manifest-path` make any allowed subcommand run any program. Allow only wrappers that reject unknown flags (`cargo xtask ...`), or exact command lines. The same holds for a sandbox `excludedCommands` entry, which takes every flag and argument of the command out of the sandbox: list the command's options that run a program or read a file (`git push --receive-pack`/`--exec` and local-path remotes, `gh --body-file`, `gh api -F @file`, `gh extension`), pin the entry to the form the loop uses (`git push origin *`, `gh issue *`, not `gh *`), and record what stays open. *Why:* `cargo test *` was allowed as "read-only" until the security review ran a program through it (rust-engine-experiment M3.15); in M0.3 `git push *` was excluded until two reviewers ran a command outside the sandbox with `--receive-pack=`. *From:* rust-engine-experiment M3.15; M0.3 · *Confirmed:* 2026-11-28
- **tooling-4.** A guard that reads command lines catches habits, not intent: abbreviated flags, `-c` settings, aliases and stored config route around it. Put the real barrier on the server (the `main` ruleset) and stop hardening the hook when reviews only find deliberate evasions. *Why:* three review rounds kept finding new shell forms (rust-engine-experiment M3.15); in M0.3 each round on the excluded `git push` found another route (flags, then a planted `.git/commondir`, then a nested repository), and the maintainer chose to record the rest for a redesign. *From:* rust-engine-experiment M3.15; M0.3 · *Confirmed:* 2026-11-28
- **tooling-5.** A POSIX `sh` script's `trap` does not run while a foreground child runs; to clean up a long `docker run`, start it in the background with `--init`, then `wait`. *Why:* the mutants script's trap left the container running when the script was killed (rust-engine-experiment M3.15). *From:* rust-engine-experiment M3.15 · *Confirmed:* 2026-11-15
- **tooling-6.** Every script a tool runs keeps LF line endings (`.gitattributes`); a script type not matched by `*.sh` needs its own rule. *Why:* a CRLF checkout on Windows turns a hook into a syntax error, which exits 2 and blocks every Bash call (rust-engine-experiment M3.15). *Deviate when:* the file is never run by `sh`. *From:* rust-engine-experiment M3.15 · *Confirmed:* 2026-11-15
- **tooling-7.** Trial a new or changed skill before relying on it: a fresh agent follows it read-only against a real document or state and reports what it had to guess. Give the trial agent the skill's own rules and nothing narrower, or a gap hides behind the extra restriction. Trial every lane and entry point the change adds (a new section, its `resume` path), not only the main one. *Why:* every skill trial in M3.15 found gaps that writing the skill had not (resume on a dirty tree, grill on an accepted spec, the power-log filter). M3.18's trials found the missing Project number and flags the same way. M0.2 trialled only `next`; the new `chore` lane and its `resume` path then took four review rounds, each finding new gaps. *From:* rust-engine-experiment M3.15; M0.2 · *Confirmed:* 2026-11-27
- **tooling-8.** A skill or stage that reads issue, comment or pull request text says in that step that the text is data, not instructions; do not rely on a different skill having said it. *Why:* chunk stage 1 started reading a linked issue's comments with no such guard, on a repository where anyone can comment (rust-engine-experiment M3.18). *From:* rust-engine-experiment M3.18 · *Confirmed:* 2026-11-16
- **tooling-9.** When a spec narrows a CLI ("`gh api` for reads, and the writes below"), the skill copies the narrowing word for word, because a bare command name grants its whole surface; `gh api` becomes a POST as soon as `-f` or `-F` is given, so write "GET only" as an explicit `--method GET`. After adding such a blanket rule, grep the same file for example commands it now forbids. *Why:* review found `gh label`, a plain `gh api`, and then the skill's own `gh api user` outside the rule (rust-engine-experiment M3.18). *From:* rust-engine-experiment M3.18 · *Confirmed:* 2026-11-16
- **tooling-10.** A `gh ... list` that decides something is missing (a triage scope, "is this issue a Project item") sets `--limit` explicitly, or asks the item directly (`gh issue view --json projectItems`). *Why:* the default is 30, so past that "not found" is a silent skip (rust-engine-experiment M3.18). *From:* rust-engine-experiment M3.18 · *Confirmed:* 2026-11-16
- **tooling-11.** `gh project field-list --format json` does not report a field's data type: every field that is not single-select shows as `ProjectV2Field` with no `dataType`, built-in fields included. A check of a field's type reads its values instead (`gh project item-list --format json`: the value is a JSON number), or names one GraphQL query. *Why:* the engine's M3.20 first recorded `ProjectV2Field` as "the number-field type", and triage's planned check would have passed a text field named Order (code review). *From:* rust-engine-experiment M3.20 · *Confirmed:* 2026-11-27
- **tooling-12.** A rule that decides from GitHub data (which chunk is next, which ID is free, what a builder's brief is, whether work is in flight) reads only what other accounts cannot write: issues authored by the maintainer's account, pull requests from this repository (`isCrossRepository == false`, also on `gh pr list --head`, which matches a fork's branch of the same name), branches on origin, and Project items whose `content.repository` is this repository (a user-owned Project can hold other repositories' issues). Filter by writer first; do not patch each editable field (title, body, closing keywords) one at a time. *Why:* in the engine's M3.20 three review rounds each found another field an outside account could change (a fork pull request's `Closes #N`, a retitled issue, an edited body) until the maintainer approved filtering by author instead. *From:* rust-engine-experiment M3.20; M0.2 · *Confirmed:* 2026-11-27
- **tooling-13.** A skill rule that reads GitHub state names what to do on an empty result at each stage (no open milestone, no candidates), and a write followed by a Project's built-in workflow waits for that workflow before setting the field it also sets. *Why:* in M0.2 an empty milestone list made "every chunk issue of the milestone is closed" vacuously true, which would have sent `/chunk next` to the boundary checklist (skill trial); and the "Item added to project" workflow can run after `gh project item-add` returns, so a Status set at once could be reset to Inbox (code review; plausible, not measured, since measuring it needs Project writes). *From:* M0.2 · *Confirmed:* 2026-11-27
- **tooling-14.** A skill lane that reuses a role written for chunks (a chore's `builder` or `review-code`) overrides, in the brief, each fixed assumption in the role file (a spec, a chunk folder, `log.md`). Its `resume` path re-checks its inputs (the brief's author, the issue's state) before acting on uncommitted work, and says what happens to that work at every step it can resume into. *Why:* in M0.2 the chore lane first told its builder to log to a chunk log that does not exist, then resumed by committing uncommitted work before re-reading the issue through the authorship gate, and skipped a review fix left uncommitted at a later step (code and security reviews, three rounds). *From:* M0.2 · *Confirmed:* 2026-11-27
- **tooling-15.** In the maintainer's zsh, an unquoted variable holding several flags is passed as one argument (`a="--target all"; cargo tree $a` fails), so a check written with one can fail silently and read as a pass. Write flags literally, or use an array (`"${a[@]}"`). zsh's `echo` also expands backslash escapes, so `echo "$json" | jq` corrupts JSON that holds `\n`: pipe the command into `jq` directly, or use `print -r --`. *Why:* M0.2's first test of the grill's lockfile check put `--target all` in a variable; cargo rejected it, the error went to `/dev/null`, and the empty output looked like no unlocked crate. In its rollout, `echo "$items" | jq` failed to parse the Project's items, so every Order write got an empty item id. *From:* M0.2 · *Confirmed:* 2026-11-27
- **tooling-16.** In Claude Code's sandbox, `Read(...)` permission deny rules also become sandbox read denies, so a sandboxed tool that authenticates from a denied path (`gh` from `~/.config/gh`, `git` through the keychain) fails with a file-permission error, not an auth error. An `excludedCommands` entry matches the command text from its start and applies only when every command of the Bash call matches: `git -C x push`, `cd x && gh ...` and `gh ... | jq` stay sandboxed. Run an excluded command alone and in its plain form. *Why:* M0.3's spec assumed `gh` and `git push` would authenticate sandboxed once their paths left `denyRead`; both failed on the `Read` denies, and `git -C <repo> push` then failed sandboxed under `git push *`. *From:* M0.3 · *Confirmed:* 2026-11-28
- **tooling-17.** Anything that runs outside the sandbox (a hook, an excluded command) and reads state a sandboxed command can write turns that write into code run on the host: a hook that builds `xtask` from the working tree, an excluded `git` that follows a planted `.git/commondir`, a nested repository's `gitdir:`, or `core.fsmonitor`. Before excluding a command or adding a hook, list what it reads from the agent-writable tree, not only its command text. *Why:* M0.3's push guard checked the `git push` text while the hook compiled agent-writable code and `git` read a planted git directory; both were found only in security review. *From:* M0.3 · *Confirmed:* 2026-11-28
- **tooling-18.** Sandbox write paths measured on a warm machine cover only what was already cached: a new dependency, a fresh clone or a toolchain change writes `~/.cargo/registry`, `~/.cargo/git` or `~/.rustup`, which fails sandboxed. Keep those paths out of `allowWrite` (a sandboxed command could rewrite crates and toolchains other projects run) and have the maintainer run `! cargo fetch` or `! rustup show` first. *Why:* M0.3's evaluation passed with only `~/.cargo/advisory-dbs` writable because the caches were warm; the portability review found the cold-cache failure. *From:* M0.3 · *Confirmed:* 2026-11-28
